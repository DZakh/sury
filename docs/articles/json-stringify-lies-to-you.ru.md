Помните, как 5-7 лет назад все использовали [Yup](https://github.com/jquense/yup) или [Ajv](https://ajv.js.org/) и были этим искренне довольны? Должен признать, половина интернета довольна до сих пор 🫡

Потом вышло ["Parse, don't validate"](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/) и стало настольной книгой для многих разработчиков, а затем выстрелило и в мире JavaScript/TypeScript. Тысячи схема-библиотек для парсинга — доказательство 😁

Ну... это уже решено, и не за этим вы открыли статью. Что не решено — так это:

- **"Encode, don't stringify"**

Или другими словами: **НИКОГДА не используйте `JSON.stringify` в своём коде.** - Да, сейчас это горячий тейк!

Дайте я это докажу и сделаю статью переломным моментом для JavaScript-экосистемы так же, как ["Parse, don't validate"](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/) сделал это в 2019. Поехали!

## Часть 1: сплошная ложь

Что не так с `JSON.stringify`, спросите вы? С API, который есть почти в каждом проекте. Что ж, давайте посчитаем, сколько у вас дыр в ботинках. Думаю, я собрал их все за свои 7 лет разработки. Напишите в комментариях, если `JSON.stringify` вам ни разу не соврал - я удивлюсь 👀

### Он возвращает `undefined`

```ts
JSON.stringify(undefined);
// => undefined

JSON.stringify(() => {});
// => undefined
```

Кто-то скажет — ну ок... но посмотрите на возвращаемый тип в TypeScript:

```ts
stringify(value: any, replacer?: ..., space?: ...): string;
```

Аргумент `any` делает это особенно приятным. Не буду объяснять, как это может выйти боком.

Есть хороший инструмент [ts-reset](https://github.com/mattpocock/ts-reset), но здесь он вас не спасёт - он патчит `JSON.parse` и вообще не поставляет правила для `JSON.stringify`.

### Он падает

```ts
JSON.stringify({ id: 1n });
// => TypeError: Do not know how to serialize a BigInt

const user = {};
user.self = user;
JSON.stringify(user);
// => TypeError: Converting circular structure to JSON

let root = {},
  node = root;
for (let i = 0; i < 50000; i++) node = node.next = {};
JSON.stringify(root);
// => RangeError: Maximum call stack size exceeded
```

Последние 2 — настоящие краевые случаи за рамками темы статьи, но я всё равно добавлю пример в коллекцию необработанных ошибок.

### Ошибки не говорят, где искать

Когда он всё-таки бросает исключение, начинаются прятки:

```ts
JSON.stringify({ user: { orders: [{ total: 1n }] } });
// => TypeError: Do not know how to serialize a BigInt
```

В этот момент вы буквально слепы, а стек-трейс говорит вам только про `res.json()` - не сильно-то помогает.

### Он молча портит ваши данные

Вот эту часть хочу подсветить. Она может стоить реальных денег. Ни падения, ни предупреждения, и очень легко пропустить:

```ts
JSON.stringify({ price: Infinity }); // => '{"price":null}'
JSON.stringify({ price: NaN }); // => '{"price":null}'
// Ваша математика переполнилась. Клиент рисует пустую ячейку или падает

JSON.stringify({ a: undefined, b: 1 }); // => '{"b":1}'      ключа больше нет
JSON.stringify([1, undefined, 2]); // => '[1,null,2]'   то же значение, теперь null
JSON.stringify([1, () => {}, 2]); // => '[1,null,2]'
// Может, для вас это ожидаемо, но не для проверки T | null на другой стороне

JSON.stringify({ m: new Map([["a", 1]]) }); // => '{"m":{}}'
JSON.stringify({ s: new Set([1, 2]) }); // => '{"s":{}}'
// Просто потеряли данные и никакой ошибки

JSON.stringify({ b: new Uint8Array([1, 2, 3]) });
// => '{"b":{"0":1,"1":2,"2":3}}'
// Массив байтов стал словарём, с которым никто не знает что делать
```

Самая большая проблема в том, что это проходит незамеченным, и иногда даже TypeScript от этого не защитит.

### Он отправляет всё, что найдёт

```ts
JSON.stringify({ login: "hello", _internalSecret: "1232" });
// => '{"login":"hello","_internalSecret":"1232"}'
```

Нет никакого списка полей, которые вы одобрили - всё, что лежит на объекте, уходит в сеть. Сомневаюсь, что это будет прямо секрет, а вот какое-нибудь внутреннее состояние - запросто.

## Часть 2: encode, don't stringify

Раз вы всё ещё читаете статью, думаю, вы уже сталкивались хотя бы с одной из этих ошибок `JSON.stringify`. Рад видеть вас здесь 🤝

Решение простое, и идея та же, что в "Parse, don't validate". `JSON.stringify` не знает, какими ваши данные должны быть, поэтому он угадывает. Вместо этого для каждого типа приложения перед сериализацией нужно создать энкодер, который безопасно превратит значение в валидный JSON или сразу в JSON-строку:

```ocaml
type user = {
  name : string;
  age : int;
}

let user_to_json { name; age } =
  `Assoc [
    ("name", `String name);
    ("age", `Int age);
  ]

let json = user_to_json { name = "Alice"; age = 42 }

let output = Yojson.Safe.to_string json
(* {"name":"Alice","age":42} *)
```

Я взял OCaml, потому что он, по-моему, идеально показывает идею в её основе и то, как люди справлялись с этим в «серьёзных» языках годами. Единственная деталь: в реальных сценариях энкодеры обычно порождаются из определений типов - как это делает [Typia](https://typia.io/) в мире JavaScript.

Мне же больше нравится рантайм-схема. Все современные JavaScript схема-библиотеки уже являются источником правды для наших моделей данных, с выводом типов из коробки. И если схема уже описывает данные на _входе_, она может описать данные и на _выходе_ — из того же определения.

Это то, что [**Sury**](https://github.com/DZakh/sury) первым сделал в мире JavaScript-схем. Одна схема, оба направления:

```ts
import * as S from "sury";

const schema = S.schema({
  id: S.bigint,
  at: S.date,
  price: S.number,
});
//? Schema<{id: bigint, at: Date, price: number}, {id: bigint, at: Date, price: number}>

const encodeToJsonString = S.encoder(schema, S.jsonString);
//? (data: {id: bigint, at: Date, price: number}) => string

encodeToJsonString({
  id: 9007199254740993n,
  at: new Date("2026-01-15T10:30:00.000Z"),
  price: 9.99,
});
// => '{"id":"9007199254740993","at":"2026-01-15T10:30:00.000Z","price":9.99}'

// или
const encodeToJson = S.encoder(schema, S.json);
//? (data: {id: bigint, at: Date, price: number}) => JSON

// или (скоро)
const encodeToBase64url = S.encoder(schema, S.base64url);
//? (data: {id: bigint, at: Date, price: number}) => string

// или безопасно раскодировать обратно
S.decoder(
  S.jsonString,
  schema,
)('{"id":"9007199254740993","at":"2026-01-15T10:30:00.000Z","price":9.99}');
// => {id: 9007199254740993n, at: new Date("2026-01-15T10:30:00.000Z"), price: 9.99}
```

Типы, которые `JSON.stringify` отказывается принимать, автоматически преобразуются по логике из определения схемы. Невалидные значения явно падают с путём вместо тихой порчи данных. Необъявленные поля вырезаются, и всё это удобно, компактно, быстро и типобезопасно.

```ts
encodeToJsonString({ id: 1n, at: new Date(), price: Infinity });
// => throws SuryError: Failed at ["price"]: Expected JSON, received Infinity
```

Промежуточного объекта тоже нет. `encodeToJsonString` — это функция, сгенерированная ровно под эту форму:

```js
(i) => {
  let v0 = i["price"];
  return (
    '{"id":"' +
    i["id"] +
    '","at":"' +
    i["at"].toISOString() +
    '","price":' +
    (Number.isFinite(v0) ? v0 : e[1](v0)) +
    "}"
  );
};
```

Это весь скомпилированный энкодер. Единственная проверка, оставшаяся в рантайме, — это `Number.isFinite`, которая допустима при парсинге из unknown, но не при кодировании в JSON.

## Часть 3: что ещё есть

Компиляция энкодера из схемы — не новая идея. Давайте пройдёмся по всем доступным сегодня решениям, чтобы у вас была полная картина.

**Заброшенные.** `compile-json-stringify` и `slow-json-stringify` не трогали с 2022 года, а `@deepkit/type` — это трансформация на этапе сборки с последним релизом в сентябре 2025. Почему это важно: `slow-json-stringify` не экранирует кавычки, так что `{ name: 'he said "hi"' }` сериализуется в `{"name":"he said "hi""}` - баг, роняющий парсинг, который лежит там четыре года. Не рекомендую ими пользоваться.

**Прототип команды [ElysiaJS](https://elysiajs.com/).** [json-accelerator](https://github.com/elysiajs/json-accelerator) — интересный прототип от людей, стоящих за одним из самых быстрых HTTP-фреймворков в JavaScript-экосистеме. Но он так и не попал внутрь самого фреймворка, у него не было релизов с апреля 2025, и он вообще не делает валидации - он приводит типы у всего, что вы ему передадите, так что `{ price: Infinity }` выходит как `{"price":Infinity}`, что даже не является валидным JSON. Цель проекта была в том, чтобы сделать более быстрый `JSON.stringify`, а не починить корректность - его я тоже не рекомендую.

**Форматы передачи.** [devalue](https://github.com/sveltejs/devalue) (SvelteKit) и [superjson](https://github.com/ravionhq/superjson) (tRPC) огромны - вместе около 20M загрузок в неделю - и они решают другую задачу:

```ts
const value = {
  at: new Date("2026-01-15T10:30:00Z"),
  price: Infinity,
  secret: "LEAKED",
};

devalue.stringify(value);
// => [{"at":1,"price":-4,"secret":2},["Date","2026-01-15T10:30:00.000Z"],"LEAKED"]

superjson.stringify(value);
// => {"json":{"at":"2026-01-15T10:30:00.000Z","price":"Infinity","secret":"LEAKED"},
//     "meta":{"values":{"at":["Date"],"price":["number"]},"v":1}}
```

Они делают так, что `bigint`, `Date`, `Map` и даже циклические ссылки переживают round trip, и добиваются этого, изобретая собственный формат передачи. Я рекомендую это решение за простоту, когда вы контролируете оба конца — и парсинг, и сериализацию — и не контролируете структуру отправляемых данных (схема неизвестна). Но это формат передачи, который сторонние потребители не поймут, а отсутствие схемы приводит к той же проблеме неконтролируемых данных, что и у `JSON.stringify`.

**[typia](https://typia.io/)** читает ваши TypeScript-типы на этапе сборки и генерирует из них сериализатор. `typia.json.assertStringify<T>()` сначала валидирует и указывает на поле - `invalid type on $input.id` - так что это действительно безопасно, а рантайм-стоимость близка к нулю, потому что всё заинлайнено на этапе сборки. Плата — сама сборка: вам нужен `ttsc` или unplugin, это не запустить из чистого JavaScript, и нет рантайм-значения схемы, которое можно было бы передать куда-то ещё. `bigint` к тому же [прямо запрещён](https://github.com/samchon/typia/issues/444) в его JSON-функциях, так что для него снова ручной маппер. Рекомендую, если вам нравятся compile-time инструменты.

**[Effect Schema](https://effect.website/)** имеет двунаправленные кодеки уже много лет, и в v4 у него самый сильный ответ после Sury. Идиоматичный способ — `toCodecJson`, который превращает любую схему в JSON-совместимую:

```ts
const codec = S.toCodecJson(S.Struct({ id: S.BigInt, at: S.Date }));

S.encodeSync(codec)({ id: 42n, at: new Date("2026-01-15T10:30:00Z") });
// => { id: "42", at: "2026-01-15T10:30:00.000Z" }
```

`bigint`, `Date` и `Uint8Array` обрабатываются автоматически, без wire-логики в определении схемы. Единственное, что стоит знать, — как он поступает со значениями, которых в JSON быть не может: `Infinity` становится строкой `"Infinity"` и прекрасно раскодируется обратно. Отлично, если оба конца говорят на Effect, и неожиданно для потребителя на другом языке, который ждал там число. Sury вместо этого падает, и я считаю это более безопасным поведением по умолчанию для публичного API, но назвать это ложью было бы нечестно - ничего не теряется.

При всём этом роасте я бы назвал Effect v4 лучшей TypeScript-библиотекой 2026 года, а Effect Schema — очевидным выбором, если вы уже используете Effect.

**[Zod](https://zod.dev/codecs)** получил кодеки в 4.1, и он ближе всех:

```ts
z.encode(schema, { price: Infinity, name: "a" }); // ❌ throws
```

Правда, этот случай работает только потому, что `z.number()` и так отвергает `NaN` и `Infinity`, а не потому, что он знает, что целью является JSON. А для продвинутых типов вроде `bigint` или `Date` вам нужны написанные вручную кодеки, привязанные к определению схемы. Это не так плохо; важно то, что он полностью решает проблему небезопасности `JSON.stringify`. Прямой цели «JSON-строка» тоже нет, но после того как вы выполнили encode на основе схемы, `JSON.stringify` больше не опасен. Если вы уже используете Zod, рекомендую перейти на энкодеры вместо небезопасного stringify.

**[fast-json-stringify](https://github.com/fastify/fast-json-stringify)** (тот самый, от Fastify) — самый используемый, но он сохраняет часть лжи и добавляет новую:

```ts
const stringify = fastJson({
  type: "object",
  properties: { price: { type: "number" }, name: { type: "string" } },
  required: ["price", "name"],
});

stringify({ price: Infinity, name: "a" }); // => '{"price":null,"name":"a"}'   всё ещё портит
stringify({ price: NaN, name: "a" }); // => throws: The value "NaN" cannot be converted to a number
stringify({ price: 1, name: 42 }); // => '{"price":1,"name":"42"}'     молча привёл тип
```

Молчаливое приведение типов — не баг, его типы буквально объявляют `StringCoercible = string | Date | RegExp` - но мне понадобилось время, чтобы понять, что не так.

Главная причина такого поведения в том, что схема вообще не доходит до TypeScript:

```ts
// fast-json-stringify — <TDoc extends object = object>(doc: TDoc) => string
stringify({ totally: "unrelated", nonsense: 123 }); // ✅ компилируется, strict mode

// Sury — (data: { price: number; name: string }) => string
encode({ totally: "unrelated", nonsense: 123 });
// => TS2353: 'totally' does not exist in type '{ price: number; name: string }'
```

В эпоху AI игнорировать типы, которые даёт схема, — это бесплатный билет к забавным багам. При этом у [**Sury**](https://github.com/DZakh/sury) есть `S.fromJSONSchema`, который корректно выводит типы даже из рекурсивных определений JSON Schema. `fast-json-stringify` я бы не рекомендовал - он не добавляет ни производительности, ни гарантий корректности.

В общем, всё рядом:

| Отсутствующее поле                    | ✅ падает с путём   | ✅ падает с путём     | ✅ падает с путём   | ✅ падает с путём    | ✅ падает (только имя)   |

Размеры измерены с tree-shaking. `fast-json-stringify` — единственный здесь, кто портит и приводит типы, ничего вам не говоря, и добавление [Ajv](https://ajv.js.org/) перед ним исправляет это примерно за 46 байт, потому что он и так зависит от Ajv.

## Часть 4: «а разве кодирование не медленное?»

Это спор, который я часто слышал, когда 5 лет назад люди начали тащить схемы для парсинга в каждый проект. Здесь ситуация ровно та же — вы меняете дополнительную логику на корректные исходящие данные. Но моя мысль в том, что это может быть выигрышный обмен, ещё и с улучшением производительности.

Вот полный бенчмарк, все строки, включая те, где я проигрываю:

## Часть 5: как я обогнал аппаратно ускоренный `JSON.stringify`?

`JSON.stringify` — это C++ внутри движка, вылизанный за два десятилетия. Расскажу, как [Sury](https://github.com/DZakh/sury) умудряется быть быстрее.

**JIT.** Sury использует Just-In-Time компиляцию через `new Function`, чтобы генерировать оптимизированный код в рантайме. Подход проверен временем и не имеет известных проблем с безопасностью. Так же работают TypeBox, Zod v4 и ArkType, и даже Cloudflare Workers недавно добавили поддержку `eval`.

**Схема уже сделала работу.** `JSON.stringify` вынужден выяснять форму вашего объекта при каждом вызове - обойти ключи, разветвиться по типу каждого значения, экранировать каждую строку. Sury делает всё это один раз, когда вы создаёте энкодер. В рантайме остаётся конкатенация строк, которую движки оптимизируют ничуть не хуже.

**Никакого промежуточного объекта.** Вот это упускают остальные решения. Даже если вы пишете мапперы руками, вы сначала собираете целый новый объект - `{ id: String(id), at: at.toISOString() }` - и потом отдаёте его в `JSON.stringify`, который обходит его заново. Аллокация плюс второй проход. Sury идёт сразу в строку.

**А там, где `JSON.stringify` выигрывает, Sury просто вызывает его.** Длинные строки, форматированный вывод, поддеревья, которые и так уже обычный JSON. Никакой гордости 😁

## Вам не нужно переписывать проект

Может, вам нравится [Zod](https://github.com/colinhacks/zod), или [Valibot](https://valibot.dev/), или [TypeBox](https://github.com/sinclairzx81/typebox), и я сомневаюсь, что вы собираетесь мигрировать кодовую базу из-за того, что какой-то незнакомец на dev.to написал разнос `JSON.stringify`...

И не нужно. Всё, что умеет отдавать JSON Schema, может передать свои схемы в [Sury](https://github.com/DZakh/sury), и Sury вернёт вам типизированный, скомпилированный, безопасный энкодер:

```ts
const surySchema = S.fromJSONSchema(
  yourExistingSchema["~standard"].jsonSchema.input({ target: "draft-07" }),
);

S.encoder(surySchema, S.jsonString); // безопасный jsonString-энкодер
S.encoder(surySchema, S.json); // безопасный json-энкодер
S.encoder(S.any, surySchema, S.json); // безопасный json-энкодер с валидацией
S.assert(surySchema, data); // быстрая валидация с путями в ошибках
```

Оставьте свои схемы там, где они есть. Используйте [Sury](https://github.com/DZakh/sury) как ускоритель в инфраструктурном слое - на границе сериализации, на горячем эндпоинте, у продюсера очереди - и не трогайте остальное приложение. Митинг про миграцию не требуется.

(Если фраза [_Standard JSON Schema_](https://standardschema.dev/json-schema) вам пока ни о чём не говорит: это спека, благодаря которой это работает между библиотеками, притом что ни одна из них не знает об остальных. Подписывайтесь - это одна из следующих статей.)

Мы перестали доверять невалидированному _входу_ много лет назад. Пора перестать доверять невалидированному _выходу_.
