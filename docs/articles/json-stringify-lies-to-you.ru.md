`JSON.stringify` — выбор по умолчанию и, кажется, единственный выбор практически в любом JavaScript-проекте. Он встроенный, быстрый, не требует зависимостей и притворяется безопасным выбором.

Он же ответственен за огромное количество продакшн-багов. Неправильные денежные значения. Таймстемпы, которые возвращаются строками. Поля, которые тихо исчезают между сервером и клиентом. Падения на payload, который в другом месте работал нормально.

Моё мнение: **НИКОГДА не используйте `JSON.stringify` в своём коде.**

Уф, это громко, дайте я это обосную.

## FAQ перед началом

**«Никогда? Серьёзно?»**
Для сериализации данных вашего приложения — да, серьёзно. Для `console.log`, ключа кэша или быстрого дебаг-дампа — может быть и нормально, но я всё равно не рекомендую.

**«Это реклама?»**
Отчасти да — я написал [**Sury**](https://github.com/DZakh/sury), я им горжусь и считаю, что он это решает. Но первая половина статьи — это чистый JavaScript, и каждая проблема в ней существует независимо от того, установите вы что-то моё или нет.

**«И бенчмарки подтасованы?»**
Я опубликовал и те строки, где **Sury** проигрывает. Они ниже.

## Часть 1: он совершенно небезопасен

### Он возвращает `undefined`

```ts
JSON.stringify(undefined);
// => undefined

JSON.stringify(() => {});
// => undefined
```

Не строку `"undefined"`. Само значение. Из функции с таким типом:

```ts
stringify(value: any, replacer?: ..., space?: ...): string;
```

Тип говорит `string`, ну... ок... Так что TypeScript спокойно позволит вам написать `JSON.stringify(x).length` и выдаст вам алерт в Sentry в 3 часа ночи. И нет, [ts-reset](https://github.com/mattpocock/ts-reset) вас здесь не спасёт — он патчит `JSON.parse`, а для `JSON.stringify` не поставляет вообще никакого правила.

### Он падает

```ts
JSON.stringify({ id: 1n });
// => TypeError: Do not know how to serialize a BigInt

const user = {};
user.self = user;
JSON.stringify(user);
// => TypeError: Converting circular structure to JSON

let root = {},
  node = root;
for (let i = 0; i < 50000; i++) node = node.next = {};
JSON.stringify(root);
// => RangeError: Maximum call stack size exceeded
```

Последние 2 — действительно краевые случаи, и `try/catch` с ними справится. Но давайте честно — когда вы в последний раз оборачивали `JSON.stringify` в `try/catch`? Особенно зная, что он может выдать вам `undefined`, `TypeError` или `RangeError` — в зависимости от дня.

### Ошибки не говорят вам, где искать

Когда он всё-таки бросает исключение — начинаются прятки:

```ts
JSON.stringify({ user: { orders: [{ total: 1n }] } });
// => TypeError: Do not know how to serialize a BigInt
```

Какой заказ? Какое поле? Выяснять вам придётся самостоятельно. Ну хотя бы есть стек-трейс... а, он знает только про вызов `res.json()` — ну, не сильно-то и помогает.

### Он молча портит ваши данные

Вот эта часть реально стоит денег. Ни падения, ни предупреждения — просто отрицательный баланс в вашем банковском приложении:

```ts
JSON.stringify({ price: Infinity }); // => '{"price":null}'
JSON.stringify({ price: NaN }); // => '{"price":null}'
// Ваша математика переполнилась. Клиент рисует пустую ячейку. Никому не сказали.

JSON.stringify({ a: undefined, b: 1 }); // => '{"b":1}'      ключа больше нет
JSON.stringify([1, undefined, 2]); // => '[1,null,2]'   то же значение, теперь null
JSON.stringify([1, () => {}, 2]); // => '[1,null,2]'
// Одно значение, два вкуса порчи — в зависимости от того, где оно лежит

JSON.stringify({ m: new Map([["a", 1]]) }); // => '{"m":{}}'
JSON.stringify({ s: new Set([1, 2]) }); // => '{"s":{}}'
// Ваши данные не выжили. Вы получили пустой объект и никакой ошибки.

JSON.stringify({ b: new Uint8Array([1, 2, 3]) });
// => '{"b":{"0":1,"1":2,"2":3}}'
// Массив байтов стал словарём индексов, в три раза больше по размеру
```

Ни один из них не сказал вам, что что-то пошло не так.

### Он отправляет всё, что найдёт

```ts
JSON.stringify({ login: "hello", _internalSecret: "1232" });
// => '{"login":"hello","_internalSecret":"1232"}'
```

Нет никакого списка полей, которые вы одобрили — всё, что лежит на объекте, уходит в сеть. Добавьте колонку в модель базы данных, и она может оказаться в ответе вашего публичного API в тот же день, при том что в вашем коде ничего не изменилось, чтобы вам об этом сказать.

## Часть 2: encode, don't stringify

За последние пять лет **«parse, don't validate»** стал настоящим трендом в мире JavaScript. Мы перестали проверять, нормальные ли данные, и начали превращать их в тип, которому можно доверять — на границе, один раз.

Я думаю, следующие три года принадлежат второй половине этой идеи: **encode, don't `JSON.stringify`.**

Мысль ровно та же. `JSON.stringify` не знает, какими ваши данные должны быть, поэтому он угадывает. Схема знает. И если она уже описывает данные на _входе_, она может описать данные на _выходе_ — из того же определения.

Это то, что [**Sury**](https://github.com/DZakh/sury) первым делает в мире JS-схем. Одна схема, оба направления:

```ts
import * as S from "sury";

const schema = S.schema({
  id: S.bigint,
  at: S.date,
  price: S.number,
});

const encode = S.encoder(schema, S.jsonString);

encode({
  id: 9007199254740993n,
  at: new Date("2026-01-15T10:30:00.000Z"),
  price: 9.99,
});
// => '{"id":"9007199254740993","at":"2026-01-15T10:30:00.000Z","price":9.99}'
```

Типы, которые `JSON.stringify` отказывается принимать, здесь — обычные поля. Значения, которые он молча портит, вместо этого бросают ошибку — с путём. А поля, которые вы не объявили, просто не выходят наружу:

```ts
encode({ id: 1n, at: new Date(), price: Infinity });
// => throws S.Error: Failed at ["price"]: Expected JSON, received Infinity
```

Промежуточного объекта тоже нет. `encode` — это функция, сгенерированная ровно под эту форму:

```js
(i) => {
  let v0 = i["price"];
  return (
    '{"id":"' +
    i["id"] +
    '","at":' +
    e[0](i["at"].toISOString()) +
    ',"price":' +
    (Number.isFinite(v0) ? v0 : e[1](v0)) +
    "}"
  );
};
```

Это весь энкодер — нет, я не обрезал его для статьи. Единственная проверка, оставшаяся в рантайме, — это `Number.isFinite`, та самая, которая превращает молчаливую порчу данных в ошибку.

### Одна схема, оба направления

И в обратную сторону это работает бесплатно — не нужен второй маппер, который надо держать в синхронизации:

```ts
const eventSchema = S.union([
  { type: "user.created", id: S.bigint },
  { type: "user.renamed", id: S.bigint, name: S.string },
  { type: "user.deleted", id: S.bigint },
]);

const parseEvent = S.decoder(S.jsonString, eventSchema);
const encodeEvent = S.encoder(eventSchema, S.jsonString);

const event = parseEvent('{"type":"user.renamed","id":"42","name":"Dmitry"}');
// => { type: "user.renamed", id: 42n, name: "Dmitry" }

switch (event.type) {
  case "user.renamed":
    event.name; // string — TypeScript сужает тип
    break;
}

encodeEvent(event);
// => '{"type":"user.renamed","id":"42","name":"Dmitry"}'
```

Вы написали `id: S.bigint` — тип, который хотите видеть в своём коде. `bigint` не может существовать в JSON, поэтому **Sury** выводит преобразование `"42"` <-> `42n` в обе стороны. Никаких обёрток для приведения типов, никакой второй схемы для формата передачи. И никакого `JSON.parse`/`JSON.stringify` в вашем собственном коде — `S.jsonString` это просто ещё одна схема в пайплайне.

### Encode to X

Что ещё круто — `S.jsonString` это просто ещё одна схема, и вы можете заменить её на `S.json`, `S.unknown` или на что-то вроде `S.toon`/`S.formData`/`S.protobuf`, которые сейчас в разработке.

```ts
// Та же логика и те же гарантии корректности, что у S.jsonString
// но без превращения в строку
S.encoder(schema, S.json);
```

## Часть 3: я не первый

Компиляция сериализатора из схемы — не новая идея. Даже я сам начал работать в этом направлении 4 года назад 😱

Так что давайте по ним пройдёмся — начиная с тех, которые я пропускаю, и почему.

**Всё, что требует компилятора.** Есть целое семейство библиотек — [typia](https://typia.io/) лучшая из них — которые читают ваши TypeScript-типы на этапе сборки и генерируют из них сериализатор. Они быстрые, и `assertStringify` у typia действительно безопасный. Но я не хочу компилятор и работаю с рантайм-значениями. Если вы готовы его добавить — typia хороший инструмент, и я не буду с этим спорить, просто это другая сделка, не та, о которой эта статья.

**Заброшенные.** `compile-json-stringify` и `slow-json-stringify` обе не трогали с 2022 года, а `@deepkit/type` — это трансформация на этапе сборки, последний релиз в сентябре 2025. Почему это важно: `slow-json-stringify` не экранирует кавычки, так что `{ name: 'he said "hi"' }` сериализуется в `{"name":"he said "hi""}` — баг, роняющий парсинг, который лежит там четыре года.

**Прототип команды [ElysiaJS](https://elysiajs.com/).** [json-accelerator](https://github.com/elysiajs/json-accelerator) — интересный прототип от людей, стоящих за одним из самых быстрых HTTP-фреймворков в JavaScript-экосистеме. Но он так и не попал внутрь самого фреймворка, у него не было релизов с апреля 2025, и он вообще не делает никакой валидации — он приводит типы у всего, что вы ему передадите, так что `{ price: Infinity }` выходит как `{"price":Infinity}`, что даже не является валидным JSON.

**Форматы передачи.** [devalue](https://github.com/sveltejs/devalue) (SvelteKit) и [superjson](https://github.com/ravionhq/superjson) (tRPC) — огромные, вместе около 20M загрузок в неделю — и они решают другую задачу:

```ts
const value = { at: new Date("2026-01-15T10:30:00Z"), price: Infinity, secret: "LEAKED" };

devalue.stringify(value);
// => [{"at":1,"price":-4,"secret":2},["Date","2026-01-15T10:30:00.000Z"],"LEAKED"]

superjson.stringify(value);
// => {"json":{"at":"2026-01-15T10:30:00.000Z","price":"Infinity","secret":"LEAKED"},
//     "meta":{"values":{"at":["Date"],"price":["number"]},"v":1}}
```

Они делают так, что `bigint`, `Date`, `Map` и даже циклические ссылки переживают круговой рейс — и делают это, изобретая собственный формат передачи. Это всё ещё валидный JSON, просто это уже не ваши данные — так что на обоих концах должна работать одна и та же библиотека. Отлично для JS в JS, но не то, что вы отдадите потребителю OpenAPI или сервису на Python.

И формат передачи — это не схема. Здесь ничто не знает, какими ваши данные должны были быть, поэтому `Infinity` спокойно едет дальше, а `secret` уходит наружу в любом случае. Другая задача, никаких гарантий корректности.

Остаётся одна библиотека, за которой вы реально потянетесь сегодня.

**[fast-json-stringify](https://github.com/fastify/fast-json-stringify)** (та самая, от Fastify) — самая используемая, но она сохраняет часть лжи и добавляет новую:

```ts
const stringify = fastJson({
  type: "object",
  properties: { price: { type: "number" }, name: { type: "string" } },
  required: ["price", "name"],
});

stringify({ price: Infinity, name: "a" }); // => '{"price":null,"name":"a"}'   всё ещё портит
stringify({ price: NaN, name: "a" }); // => throws: The value "NaN" cannot be converted to a number
stringify({ price: 1, name: 42 }); // => '{"price":1,"name":"42"}'     молча привело тип
```

Молчаливое приведение типов — это не баг, её типы буквально объявляют `StringCoercible = string | Date | RegExp` — но мне понадобилось время, чтобы поверить, что дело не в моей схеме.

Главная причина такого поведения в том, что схема вообще не доходит до TypeScript:

```ts
// fast-json-stringify — <TDoc extends object = object>(doc: TDoc) => string
stringify({ totally: "unrelated", nonsense: 123 }); // ✅ компилируется, strict mode

// Sury — (data: { price: number; name: string }) => string
encode({ totally: "unrelated", nonsense: 123 });
// => TS2353: 'totally' does not exist in type '{ price: number; name: string }'
```

В эпоху AI игнорировать типы, которые даёт вам схема, — это бесплатный билет во множество забавных багов. При этом у [**Sury**](https://github.com/DZakh/sury) есть `S.fromJSONSchema`, который корректно выводит типы даже из рекурсивных определений JSON Schema.

В общем, всё рядом:

| Закодировать объект `{ price, name }` | **Sury** (с S.fromJSONSchema) | fast-json-stringify        | + Ajv                    |
| ------------------------------------- | ----------------------------- | -------------------------- | ------------------------ |
| `Infinity`                            | ✅ бросает с путём            | ❌ `null`                  | ✅ бросает с путём       |
| Неправильный тип                      | ✅ бросает с путём            | ❌ молча приводит          | ✅ бросает с путём       |
| Отсутствующее поле                    | ✅ бросает с путём            | ✅ бросает (только имя)    | ✅ бросает с путём       |
| `bigint` / `Date` как настоящие типы  | ✅                            | ❌                         | ❌                       |
| Необъявленные поля                    | ✅ вырезаются или запрещены   | ✅ вырезаются              | ✅ вырезаются            |
| Схема доходит до TypeScript           | ✅ выводится                  | ❌ любой объект            | ❌ любой объект          |
| Декодирует обратно тоже               | ✅ та же схема                | ❌                         | ❌                       |
| min+gzip                              | **16.4 kB**                   | 56.7 kB                    | 56.7 kB                  |

Эти размеры измерены с tree-shaking. И `+ Ajv` добавить почти бесплатно, потому что fast-json-stringify и так от него зависит — но за эти байты вы не получаете второе направление, типы или возможность написать `bigint`.

## Часть 4: «но разве `JSON.stringify` не ускорен на уровне железа?»

Я получал этот комментарий несколько раз во время разработки, и он справедливый. `JSON.stringify` — это C++ внутри движка, вылизанный за два десятилетия. Как JavaScript его обгоняет?

**Схема уже сделала работу.** `JSON.stringify` вынужден выяснять форму вашего объекта при каждом вызове — обойти ключи, разветвиться по типу каждого значения, экранировать каждую строку. **Sury** сделал всё это один раз, когда вы создали энкодер. В рантайме остаётся конкатенация строк, которую движки оптимизируют ничуть не хуже.

**Никакого промежуточного объекта.** Вот про это забывают. Даже если вы пишете мапперы руками, вы сначала собираете целый новый объект — `{ id: String(id), at: at.toISOString() }` — и потом отдаёте его в `JSON.stringify`, который обходит его заново. Аллокация плюс второй проход. **Sury** идёт сразу в строку.

**А там, где `JSON.stringify` выигрывает, Sury просто вызывает его.** Длинные строки, форматированный вывод, поддеревья, которые и так уже обычный JSON. Никакой гордости 😁

Вот полный бенчмарк, все строки, включая ту, где я проигрываю:

| Закодировать в JSON-строку              | **Sury**     | `JSON.stringify` | fast-json-stringify | devalue / superjson |
| --------------------------------------- | ------------ | ---------------- | ------------------- | ------------------- |
| Ответ API (профиль пользователя, 7 полей) | **317 ns**  | 595 ns           | 372 ns              | 3.36 - 4.88 µs      |
| Списочный эндпоинт (100 строк)          | **14.84 µs** | 15.85 µs         | 16.07 µs            | 177 - 297 µs        |
| Лента событий (50 tagged-union событий)  | **5.26 µs**  | 8.18 µs          | 21.04 µs            | 72 - 140 µs         |
| Словарь метрик (50 числовых значений)   | 11.82 µs     | **6.73 µs**      | 12.69 µs            | 34 - 51 µs          |
| Словарь лейблов (50 строковых значений) | **5.38 µs**  | 5.43 µs          | 10.83 µs            | 33 - 48 µs          |
| `bigint` id + бинарный payload + `Date` | **1.24 µs**  | 1.54 µs          | 1.49 µs             | 4.42 - 7.26 µs      |

Важно! Я не прошу вас переходить ради наносекунд. Смысл в том, что `JSON.stringify` небезопасен, и что починить это не стоит вам ничего — никакой просадки по производительности, а на большинстве реальных форм даже улучшение. Безопасность — это причина. Скорость — просто повод, с которым можно прийти к тимлиду.

## Вам не нужно переписывать проект

Может, вам нравится [Zod](https://github.com/colinhacks/zod), или [Valibot](https://valibot.dev/), или [TypeBox](https://github.com/sinclairzx81/typebox), и вы не собираетесь мигрировать кодовую базу из-за того, что какой-то незнакомец на dev.to написал разнос `JSON.stringify`. Справедливо.

И не нужно. Всё, что умеет отдавать JSON Schema, может передать свои схемы в [**Sury**](https://github.com/DZakh/sury), и **Sury** вернёт вам типизированный, скомпилированный, безопасный энкодер:

```ts
const surySchema = S.fromJSONSchema(
  yourExistingSchema["~standard"].jsonSchema.input({ target: "draft-07" }),
);

S.encoder(surySchema, S.jsonString); // безопасный jsonString-энкодер
S.encoder(surySchema, S.json); // безопасный json-энкодер
S.assert(surySchema, data); // быстрая валидация с путями в ошибках
```

Оставьте свои схемы там, где они есть. Используйте **Sury** как ускоритель в инфраструктурном слое — на границе сериализации, на горячем эндпоинте, у продюсера очереди — и не трогайте остальное приложение. Митинг про миграцию не требуется.

(Если фраза [_Standard JSON Schema_](https://standardschema.dev/json-schema) вам пока ни о чём не говорит: это спека, благодаря которой это работает между библиотеками, притом что ни одна из них не знает о других. Подписывайтесь — это одна из следующих статей.)

## Подводя итог

Я не думаю, что ваше приложение реально сломано. Куча софта прекрасно живёт на `JSON.stringify` те пятнадцать с лишним лет, что он существует.

Но в следующий раз, когда вы увидите `null` там, где должно быть число, таймстемп, вернувшийся строкой, или поле, исчезнувшее между двумя сервисами — вы будете точно знать, какая функция это сделала, и что она ни разу вас не предупредила.

Мы перестали доверять невалидированному входу много лет назад. Пора перестать доверять невалидированному _выходу_.

**Encode, don't `JSON.stringify`.** — Cheers 🙏
